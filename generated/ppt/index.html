AUC 只問一件事：模型有沒有把該抓的排在前面。不用管它怎麼算出來的。

THE PAIN · 02 · 超參要試幾次

窮舉，還是會學

50 GRID SEARCH · 網格搜尋
暴力窮舉

你先把每個設定要試的值列出來 —— C 列 5 個、max_iter 列 5 個、solver 列 2 個，它就把所有組合全部跑過一遍。

5 × 5 × 2 = 50
次訓練 · 一次都不能少
  • 你還得先決定「要試哪些值」
  • 維度再加一個，數字就再乘一次
  • 跑完你只知道這 50 組，別的不知道
20 OPTUNA · 它會學
只寫範圍

你只給每個設定一段範圍，它自己挑值去試。試一次叫一個 trial，你決定要試幾次就好。

def objective(trial): C = trial.suggest_float("C", 1e-3, 1e2, log=True) return cross_val_score(model, X, y, cv=5).mean() study.optimize(objective, n_trials=20)
  • 你只寫「範圍」，不寫要試哪些值
  • 它看前面的成績，決定下一組往哪找
  • 跑到一半發現沒救就砍掉，這招叫 pruning
試 20 次就找到好結果，網格搜尋要 50 次 —— 差別在它會學

28 / 54
兩種 JOIN · POINT-IN-TIME JOIN ＝「回到那一刻再取值」

正確做法：point-in-time join

A 錯誤 · 無時間概念的 JOIN
整張特徵表直接 join

整張特徵表取最新的值，一次對上所有訓練樣本 —— 就是平常寫慣的那一行 merge。

問題在於：那個「最新的值」，是你今天才知道的。訓練樣本是三個月前的事，它憑什麼看得到今天？

  • 混進未來才量到的特徵
  • 離線指標虛高，看起來超棒
  • 上線那刻拿不到 → 崩盤
B 正確 · POINT-IN-TIME JOIN
只取當下拿得到的

每一列訓練樣本，各自回到它自己的那個時間點，只取那一刻之前最新的一筆特徵值。

再加一個 ttl（保鮮期）：太舊的值就當作沒有，因為上線時它也早就過期了。

  • 訓練集只含當下真的拿得到的
  • 離線指標誠實，貼近上線表現
  • 訓練/服務一致，表現穩定
要做到這件事，你的資料表只需要多一欄：event_timestamp（事件時間戳記，這筆值是什麼時候量到的）—— 這一欄事後補不回來，一開始就要留

PITFALLS · 02 TRAPS

兩個一定要看懂的坑

1 坑 · 切法
一定要按時間切

感測器資料表是一台機器接一台機器排下來的，不是按時間排的。

你以為對半切是「前半段時間 vs 後半段時間」，實際切出來的是「A 機台 vs B 機台」。兩台機器本來就長得不一樣，工具當然說有漂移 —— 那不是漂移，是你切錯了。

  • 照列序對半切 = 其實是照機台切
  • 各機台平均溫度差好幾度（55.9 ~ 63.6）
  • 還沒動任何手腳，報告就說有漂移
2 坑 · 門檻
整體 False 不代表沒事

預設要超過半數欄位一起漂移，總結論才會亮紅燈（drift_share = 0.5，就是 50% 這個門檻）。

三個欄位裡只有一個漂掉 = 三分之一，沒過 50%，總結論就寫「沒有漂移」。但那一欄如果正好是模型最看重的溫度，模型早就在亂猜了。

  • 推一個欄位漂移 → 1/3 沒過門檻
  • 總結論仍是 False，看起來一切正常
  • 一個關鍵欄位漂掉就足以讓模型失效
會說謊的監控比沒有監控更糟 —— 生產環境請以逐欄結果為準
